# S4.8 — Validation et rapport

| Section | Version | Statut | Dépend de |
|---|---|---|---|
| S4.8 (numéro proposé) | 1.2.0 | 🟢 ADOPTÉE | S4.1 à S4.7 |

## 1. Quatre niveaux [B]

| Niveau | Objet | Exemples |
|---|---|---|
| 1 — Syntaxe | document JSON | JSON valide, objet racine, pas de clé dupliquée |
| 2 — Contrat local | un objet seul | champs obligatoires, énumérations, patterns, fermeture, règles conditionnelles internes |
| 3 — Intégrité référentielle | un objet et ses cibles | existence, contrat de la cible, statut de la cible, appartenance |
| 4 — Intégrité globale | le corpus, base comprise | unicités, historique, transitions, graphes, cardinalités, clés sémantiques |

**[B]** Un JSON Schema couvre au plus les niveaux 1 et 2. Aucune règle de niveau 3 ou 4 ne doit être présentée comme couverte par un JSON Schema.

**[P]** Enchaînement :

1. Un objet en ERROR de niveau 1 ou 2 est **exclu** des index des niveaux 3 et 4. Une référence vers lui produit alors `S4-REF-001`, signalée normalement.
2. Tous les niveaux s'exécutent ; on ne s'arrête jamais à la première erreur.
3. Les règles des niveaux 3 et 4 qui comparent à la révision de base s'appliquent seulement si une base est fournie, ou si la base est explicitement vide.
4. Un WARNING n'exclut jamais un objet.

### Priorité entre règles [P]

Une même cause produit **une seule** issue. Quand une règle de la colonne de gauche échoue, les règles de droite ne sont pas évaluées pour le même objet (ou le même champ) :

| Si échoue | Ne pas évaluer |
|---|---|
| `S4-SYN-001`, `S4-SYN-002`, `S4-SYN-003` | toutes les autres règles pour ce document |
| `S4-SEP-001` | toutes les autres règles pour ce document |
| `S4-ID-001` | `S4-ID-002` à `S4-ID-008`, `S4-ID-011` |
| absence d'un champ obligatoire (règle de contrat) | les règles portant sur ce champ |
| `S4-LIFE-002` | `S4-LIFE-001` |
| `S4-CUR-002` | `S4-ID-006` |
| `S4-REL-001` sur le champ `type` | `S4-REL-003`, `S4-REL-004`, `S4-REL-005`, `S4-REL-006` à `S4-REL-010` pour cette Relation |
| `S4-RB-001` ou `S4-RB-002` | `S4-RB-003` à `S4-RB-008` |
| `S4-VER-004` | `S4-VER-003` |
| `S4-MAP-008` | `S4-ID-010` |

Répartition des champs :

- Le champ `replacedBy` relève **uniquement** des règles `S4-RB-*`, jamais des règles `S4-REF-*`.
- Le champ `object` d'un CurriculumMapping relève de `S4-MAP-004` à la place de `S4-REF-002`.
- Au niveau 2, un champ de référence est contrôlé comme un identifiant valide (`S4-ID-001`). Le contrat de sa cible est contrôlé au niveau 3 (`S4-REF-002`), sauf pour les couples source/cible d'une Relation, contrôlés au niveau 2 (`S4-REL-003`).
- La présence et le type de `provenance` sur un Curriculum relèvent de `S4-CUR-014` ; sa présence sur un CurriculumMapping relève de `S4-MAP-002`. La structure interne relève des règles `S4-PROV-*`.
- La cohérence entre `type` et namespace relève de `S4-ID-003`, pas des règles « respecte son contrat ».
- Les champs `id`, `type`, `status`, `version`, `replacedBy`, `provenance`, `evidence`, `label`, `description` et `rationale` relèvent de leurs règles dédiées. Les règles « respecte son contrat » (`S4-KC-001` à `003`, `S4-REL-001`, `S4-CUR-001`, `S4-CUR-005`, `S4-CUR-011`, `S4-MAP-001`) couvrent la présence des champs obligatoires et le format des autres champs.

## 2. Corpus [P] (réponse à OPEN-019)

Un corpus S4 déclare la version de spécification qu'il suit, dans un **manifeste de corpus** :

```json
{ "specificationVersion": "1.2.0" }
```

Les objets ne portent pas de numéro de spécification. Le validateur refuse un corpus dont la version n'est pas l'une de celles qu'il implémente.

Le corpus ne contient que des objets des 8 contrats. Tout autre document est une ERROR. **[B]** Cela garantit l'exclusion des données apprenant.

## 3. Sévérités et verdict

| Verdict | Condition | Origine |
|---|---|---|
| `PASS` | 0 ERROR, 0 WARNING | [B] |
| `PASS_WITH_WARNINGS` | 0 ERROR, au moins 1 WARNING | [B] (« PASS avec avertissements ») ; [P] libellé |
| `FAIL` | au moins 1 ERROR | [B] |

**[P]** (DOC-12) Le gabarit `VALIDATION_REPORT.json` du handoff v1.1.2, qui n'autorisait que `PASS|FAIL`, est [OBSOLETE] : les règles de validation [B] définissent trois verdicts.

**[B]** Une règle bloquante (ERROR) ne dépend jamais d'une appréciation non déterministe, IA comprise. L'atomicité, la qualité d'une preuve et la rupture sémantique relèvent de la revue éditoriale, hors validateur.

## 4. Rapport

```json
{
  "specificationVersion": "1.2.0",
  "verdict": "PASS_WITH_WARNINGS",
  "errors": 0,
  "warnings": 1,
  "issues": [
    {
      "rule": "S4-REF-004",
      "severity": "WARNING",
      "message": "Référence historique vers un objet déprécié : notion.mathematiques.ancienne-notion",
      "objectId": "relation.mathematiques.exemple",
      "location": "target"
    }
  ]
}
```

| Champ d'issue | Obligatoire | Règle |
|---|---|---|
| `rule` | oui | Rule ID du catalogue |
| `severity` | oui | `ERROR` ou `WARNING`, celle du catalogue |
| `message` | oui | texte humain, déterministe (sans date ni durée) |
| `objectId` | si disponible | `id` de l'objet concerné |
| `location` | si disponible | chemin JSON Pointer dans l'objet (`/target`, `/evidence/0/locator`), ou chemin du fichier pour le niveau 1 |

**[P]** Objet porteur d'une issue de groupe :

- **Doublon de clé** (`S4-ID-009`, `S4-REL-006`, `S4-MAP-007`, `S4-CUR-004`, `S4-CUR-010`) : une issue sur chaque objet du groupe **sauf** celui dont l'`id` est le plus petit en ordre ASCII. Pour `S4-ID-009`, les objets ont le même `id` : l'issue porte sur chaque occurrence sauf la première, avec `location = document:<rang>`.
- **Cycle** (`S4-REL-007`, `S4-REL-008`, `S4-REL-009`, `S4-CUR-013`, `S4-RB-006`) : une issue par composante fortement connexe contenant un cycle, portée par le plus petit `id` en ordre ASCII parmi les objets qui forment ses arcs (Relations, ou objets portant `parent` / `replacedBy`).
- **Niveau 1** (`S4-SYN-*`, `S4-SEP-001`) : pas d'`objectId` ; `location = document:<rang>` (rang du document dans le corpus, à partir de 0).

**[P]** Ordre des issues : par `objectId` (les issues sans objet en premier), puis `rule`, puis `location`, puis `message`, en ordre ASCII.

**[P]** Code de sortie : 0 pour `PASS` et `PASS_WITH_WARNINGS`, 1 pour `FAIL`, 2 si le validateur n'a pas pu s'exécuter (corpus illisible) ou si la version de spécification n'est pas prise en charge. Dans ce dernier cas, le rapport contient la seule issue `S4-SEP-003` et le verdict `FAIL`.

## 5. Règles

| Rule ID | Niveau | Sévérité | Origine | Règle |
|---|---|---|---|---|
| S4-SYN-001 | 1 | ERROR | P | Le document est du JSON valide, encodé en UTF-8 sans BOM. |
| S4-SYN-002 | 1 | ERROR | P | La racine du document est un objet. |
| S4-SYN-003 | 1 | ERROR | P | Aucun objet JSON ne contient deux fois la même clé. |
| S4-SEP-001 | 1 | ERROR | B | Le document a un `id` dont le namespace désigne l'un des 8 contrats ; aucun autre type de document dans le corpus. |
| S4-SEP-002 | 2 | ERROR | B | Aucune propriété non déclarée par le contrat ou par la structure embarquée (contrats fermés). |
| S4-SEP-003 | 4 | ERROR | P | Le manifeste du corpus déclare une `specificationVersion` prise en charge. |
| S4-RPT-001 | V | ERROR | P | Chaque issue du rapport porte `rule`, `severity`, `message`, et `objectId` et `location` quand ils sont disponibles. |
| S4-RPT-002 | V | ERROR | B | Le verdict est `PASS`, `PASS_WITH_WARNINGS` ou `FAIL`, selon les comptes d'ERROR et de WARNING. |
| S4-RPT-003 | V | ERROR | P | Deux exécutions sur le même corpus et la même base produisent un rapport identique octet pour octet (ordre §4). |
| S4-RPT-004 | V | ERROR | P | Le code de sortie suit §4. |

**[P]** Les règles `S4-RPT-*` (niveau « V ») s'appliquent **au validateur**, pas au corpus. Elles servent de critères d'acceptation de son implémentation.

## Annexe A — Profil de sérialisation (non normatif) [P]

Proposition pour l'ADR du dépôt, sans autorité S4 :

- un objet par fichier `<id>.json`, rangé dans un dossier par namespace ;
- JSON indenté de 2 espaces, clés dans l'ordre du tableau du contrat, fin de ligne LF, une ligne vide finale ;
- manifeste de corpus `corpus.json` à la racine du référentiel ;
- révision de base = état du référentiel sur la branche principale ; révision candidate = état de la branche proposée.
