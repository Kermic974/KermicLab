# S4.2 — Cycle de vie et versionnement

| Section | Version | Statut | Dépend de |
|---|---|---|---|
| S4.2 | 1.2.0 (base : S4.2 v1.1.2, proposition Copilot) | 🟢 ADOPTÉE | S4.1, S4.6 |

**[B]** S4.2 est l'autorité transversale pour le cycle de vie, les transitions, `version`, la dépréciation, `replacedBy`, la résolubilité historique et les règles générales de nouvelles références. Elle prime sur toute autre page S4 sur ces sujets.

## 1. États canoniques [B]

| État | Sens |
|---|---|
| `draft` | en construction ou en modification, avant revue |
| `review` | soumis à contrôle avant validation |
| `validated` | utilisable comme référence canonique par les nouvelles références conformes |
| `deprecated` | conservé pour l'historique ; ne reçoit plus de nouvelle référence |

**[B]** `active` et `retired` ne font pas partie du cycle canonique. Ils sont [OBSOLETE] depuis l'audit v1.1.1 (correction 1).

## 2. Transitions

```text
draft → review          [B]
review → draft          [B]
review → validated      [B] (gates satisfaites, §7)
validated → deprecated  [B]
(aucune autre)          [B]
```

- **[P]** `deprecated` est **terminal et figé** : aucune transition sortante, aucune modification. Pour réutiliser un contenu déprécié, on crée un nouvel objet (nouvel `id`, `version = 1`).
- **[P]** Un objet **nouveau** (absent de la révision de base) a le statut `draft` ou `review`. Il ne peut pas naître `validated` ni `deprecated`.
- **[P]** Un objet `validated` ou `deprecated` dans la révision de base ne peut pas être supprimé du corpus. Un objet `draft` ou `review` peut l'être. Son `id` n'ayant jamais été publié comme référence canonique, il redevient libre.

## 3. Révision observable [P] (réponse à S42-07)

Le cycle de vie et les versions se vérifient en comparant deux états du corpus :

- la **révision de base** (dernier état accepté du référentiel) ;
- la **révision candidate** (état proposé).

Une transition est observable si l'objet existe dans les deux révisions et que son `status` diffère. Les états intermédiaires entre deux révisions acceptées ne sont pas observés. Une modification ne peut donc faire qu'**un pas** du cycle à la fois : `draft → validated` dans une même révision candidate est refusé.

Sans révision de base (premier corpus), toutes les règles de niveau 4 marquées « base » s'appliquent comme si la base était vide.

## 4. `version` (révision d'identité)

```text
id      = identité canonique
version = révision de cette identité
```

| # | Règle | Origine |
|---|---|---|
| 4.1 | `version` est un entier positif. | [B] |
| 4.2 | Pour un même `id`, les versions progressent strictement. | [B] |
| 4.3 | Un nouvel `id` commence à `version = 1`. | [P] (S42-03) |
| 4.4 | Toute modification de l'objet (n'importe quel champ autre que `version`, **statut compris**) incrémente `version` de **exactement 1** par rapport à la révision de base. | [P] (S42-03, S42-04) |
| 4.5 | Un objet non modifié garde sa `version`. | [P] |
| 4.6 | Une rupture sémantique identitaire exige un nouvel `id` avec `version = 1`. | [B] |

**[P]** La rupture sémantique n'est pas détectable automatiquement (S1-3). Elle relève de la revue. Les champs d'identité déclarés par contrat (S4.3 à S4.6) sont, eux, vérifiés : leur modification est une ERROR (`S4-ID-010`).

## 5. Références

**Définition [P]** — Une référence est un couple (champ de l'objet source, `id` cible) : `source`, `target`, `object`, `curriculum`, `stage`, `domain`, `parent`, `replacedBy`, `provenance.derivedFrom[]`. Une référence est **historique** si le même couple existait déjà dans la révision de base de l'objet source. Sinon, elle est **nouvelle**. Sans révision de base, toutes les références sont nouvelles.

| Statut de la source | Nouvelle référence vers `draft` / `review` | vers `validated` | vers `deprecated` | Référence historique vers `deprecated` |
|---|---|---|---|---|
| `draft`, `review` | autorisée [P] | autorisée [B] | **interdite** [B] | WARNING [B] |
| `validated` | **interdite** [B] (handoff) | autorisée [B] | **interdite** [B] | WARNING [B] |
| `deprecated` | — (un objet `deprecated` ne change plus, sauf passage à ce statut) | — | — | WARNING [B] |

**[D]** Une Relation est elle-même un objet : une **nouvelle** Relation (absente de la base) dont la source ou la cible est `deprecated` est une ERROR.

**[P]** (S42-01) La règle du handoff, « depuis un objet `validated`, une nouvelle référence ne cible qu'un objet `validated` », est **conservée**. Elle complète la proposition S4.2 v1.1.2, qui ne mentionnait que l'interdiction vers `deprecated`. C'est une omission, pas un conflit.

## 6. `replacedBy`

| # | Règle | Origine |
|---|---|---|
| 6.1 | Réservé aux objets `deprecated`. | [B] |
| 6.2 | Facultatif : un objet peut être déprécié sans successeur. | [P] |
| 6.3 | La cible existe et est distincte de la source. | [B] |
| 6.4 | Une **nouvelle** valeur de `replacedBy` cible un objet `validated`. | [B] |
| 6.5 | La cible est du même contrat, donc du **même namespace** (« namespace compatible »). | [B] même type ; [P] définition (S42-06) |
| 6.6 | Knowledge Core : changer de discipline (2e segment) produit un WARNING. | [P] |
| 6.7 | Une valeur **historique** dont la cible est devenue `deprecated` reste valide. La chaîne est suivie jusqu'à son terme ; si ce terme n'est pas `validated`, WARNING. | [P] |
| 6.8 | Les chaînes `replacedBy` sont acycliques. | [B] |

## 7. Gates `review → validated` [P] (réponse à OPEN-015)

Un objet ne peut porter `validated` que si toutes les règles ERROR qui le concernent sont satisfaites, en particulier :

| Contrat | Conditions supplémentaires |
|---|---|
| tous | références sortantes nouvelles vers des objets `validated` (§5) |
| MicroSkill | au moins une Relation `teaches` `validated` depuis une Notion `validated` (S4.3) |
| Skill | au moins une Relation `contributesTo` `validated` depuis une MicroSkill `validated` (S4.3) |
| Relation `requires`, `extends`, `equivalentTo` | `rationale` présent (S4.4) |
| Curriculum | `provenance.type = institutional` avec `reference` (S4.7) |
| CurriculumMapping | au moins un élément d'`evidence` (S4.6) |

**[D]** Ces conditions sont vérifiées à chaque validation, pas seulement au moment de la transition : un objet `validated` doit continuer à les satisfaire. **[P]** Exception : une condition qui ne tient plus parce qu'une cible est devenue `deprecated` produit un WARNING (référence historique), pas une ERROR.

La relecture humaine (décision pédagogique) est un processus de dépôt (revue de PR). Elle n'est pas un champ du contrat, pour ne stocker aucune donnée personnelle.

## 8. `curriculumVersion` [B]

```text
id                = identité canonique du Curriculum
version           = révision de l'enregistrement canonique
curriculumVersion = version institutionnelle (édition du programme)
```

Ces propriétés ne sont pas interchangeables. Format et usage : S4.5.

## 9. Répartition des niveaux de validation [B]

Les règles locales (vocabulaire de `status`, type de `version`) relèvent du niveau 2. Les règles historiques ou multi-objets (progression des versions, `replacedBy`, références vers des objets dépréciés) relèvent des niveaux 3 et 4. Elles ne sont **pas réductibles** au JSON Schema local.
