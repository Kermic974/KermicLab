# KermicLab — S4.2 Cycle de vie et versionnement — v1.1.2

**Version :** 1.1.2

**Statut :** 🟠 **PROPOSITION POUR VALIDATION DOCUMENTAIRE**

**Section :** S4.2 — Cycle de vie et versionnement

**Finalité :** soumettre S4.2 à validation documentaire en consolidant la règle autoritaire de cycle de vie, de révision, de dépréciation et de remplacement retenue par la baseline v1.1.1, tout en vérifiant sa compatibilité avec la mise à niveau S3.2 / S4.6 v1.1.2.

> Cette validation est documentaire. Elle ne constitue pas une validation technique des JSON Schemas, données, fixtures, validateurs, migrations ou workflows CI.

## 1. Décision proposée

Le cycle canonique commun des objets S4 est :

```text
draft → review → validated → deprecated
```

Les transitions ordinaires autorisées sont :

```text
draft → review
review → draft
review → validated
validated → deprecated
```

Les anciens états `active` et `retired` ne font pas partie du cycle canonique v1.1.2.

## 2. Portée de S4.2

S4.2 est l’autorité transversale pour le cycle de vie commun, les transitions d’état, la révision canonique, `version`, la dépréciation, `replacedBy`, la résolubilité historique et les règles générales de nouvelles références.

## 3. États canoniques

### 3.1 `draft`
Objet en cours de construction ou modification avant revue.

### 3.2 `review`
Objet soumis à contrôle avant validation. Transitions possibles : `review → draft` et `review → validated`.

### 3.3 `validated`
État utilisable comme référence canonique pour les nouvelles références conformes.

### 3.4 `deprecated`
Objet conservé pour l’historique mais qui ne doit plus recevoir de nouvelles références canoniques.

## 4. Références et dépréciation

```text
nouvelle référence vers deprecated       → interdite
référence historique devenue deprecated  → résoluble + WARNING
```

## 5. Révision canonique : `version`

```text
id      = identité canonique
version = révision de cette identité
```

`version` est un entier positif. Pour un même `id`, les révisions progressent strictement.

Une rupture sémantique identitaire exige :

```text
nouvel id
version = 1
```

## 6. Compatibilité CurriculumMapping v1.1.2

La règle spécialisée est :

```text
projectionKey = object + curriculum + stage + domain|null + role
```

`version` est exclue de `projectionKey`.

```text
même projection canonique → même id → version croissante
```

Une modification de `object`, `curriculum`, `stage`, `domain` ou `role` requiert par défaut une nouvelle identité conformément à S4.6.

## 7. `replacedBy`

`replacedBy` est réservé aux objets `deprecated`.

Sa cible doit :

1. exister ;
2. être distincte de la source ;
3. être `validated` ;
4. être du même type canonique ;
5. respecter les règles de namespace applicables ;
6. ne créer aucun cycle de remplacement.

## 8. Non-réutilisation d’identité

Un identifiant canonique historique ne doit jamais être réutilisé pour représenter un autre objet.

## 9. Version institutionnelle distincte

Pour Curriculum :

```text
id                = identité canonique
version           = révision de l’enregistrement canonique
curriculumVersion = version institutionnelle métier du Curriculum
```

Ces propriétés ne sont pas interchangeables.

## 10. Validation multi-niveaux

Les règles locales telles que le vocabulaire de `status` ou le type de `version` peuvent relever du contrat local.

Les règles historiques ou multi-objets, notamment la progression des versions, la résolution de `replacedBy`, son acyclicité et les références vers des objets dépréciés, relèvent de la validation référentielle ou globale.

## 11. Fixtures normatives attendues

### Cas valides

- objet `draft` conforme ;
- `draft → review` ;
- `review → draft` ;
- `review → validated` lorsque les gates sont satisfaites ;
- `validated → deprecated` ;
- versions successives d’un même `id` ;
- objet `deprecated` avec `replacedBy` valide ;
- référence historique vers une cible devenue `deprecated` avec `WARNING`.

### Cas invalides

- statut hors vocabulaire ;
- `active` ou `retired` utilisé comme statut canonique ;
- version non positive ;
- progression de versions incohérente ;
- `replacedBy` sur un objet non `deprecated` ;
- remplacement vers soi-même ;
- cible inexistante, non `validated` ou de type incompatible ;
- cycle de remplacement ;
- nouvelle référence vers un objet `deprecated`.

## 12. Règles normatives consolidées

1. Le cycle commun est `draft → review → validated → deprecated`.
2. `active` et `retired` sont exclus du cycle canonique v1.1.2.
3. `validated` est l’état utilisable pour les nouvelles références canoniques.
4. `deprecated` reste historiquement résoluble mais refuse les nouvelles références.
5. Une référence historique vers une cible devenue `deprecated` produit un `WARNING`.
6. `version` représente une révision d’identité et non une identité.
7. Une rupture sémantique identitaire nécessite un nouvel `id` avec `version = 1`.
8. `replacedBy` est réservé aux objets `deprecated`.
9. La cible de `replacedBy` est distincte, existante, `validated`, de même type et compatible avec le namespace attendu.
10. Les chaînes `replacedBy` sont acycliques.
11. Un identifiant historique n’est jamais réutilisé.
12. `curriculumVersion` reste distincte de `version`.
13. Les règles historiques et multi-objets ne sont pas réductibles au JSON Schema local.
